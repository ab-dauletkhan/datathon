# AI-сервис проверки кассовой дисциплины по видео

Документ для жюри Datathon 26 (ForteBank), раздел 8 технического задания.

## 1. Доступ

| что | значение |
|---|---|
| веб-интерфейс | http://79.116.80.166:10171/ |
| API | http://79.116.80.166:10171/api/v1 |

## 2. Инструкция по использованию

### Веб-интерфейс

1. Откройте адрес веб-интерфейса. Вход не нужен.
2. Загрузите видеофайл `.mov`.
3. Сервис показывает статус: место в очереди и ход обработки.
4. По завершении появляется один из двух результатов: «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений».
5. Для каждого возможного нарушения показаны тип, таймкод, описание того, что видно, правило со ссылкой на нормативный акт и 1-3 кадра-доказательства. Нажатие на нарушение перематывает видео к этому моменту.
6. Проверяющий подтверждает или отклоняет каждое нарушение. Если модель пропустила нарушение, кнопка «Добавить нарушение» под видео открывает форму: тип из каталога, начало и конец по текущему кадру, описание того, что происходит. Добавленные нарушения видны в журнале и на шкале времени и хранятся на сервере команды, без облачных сервисов. Модель от них не меняется; собранные случаи можно позже разобрать для улучшения разметки.

Результат является подсказкой для проверяющего, а не юридическим или дисциплинарным заключением.

**Камеры, без ручной загрузки.** Кнопка «Камеры» в шапке открывает страницу видеонаблюдения. Сервер принимает поток с камеры, режет его на фрагменты и сразу отправляет каждый той же модели; нарушения появляются в ленте с кадром, камерой и временем и открываются как обычная проверка. Реальной камеры на хакатоне нет, поэтому демо-камера воспроизводит записи из датасета в реальном времени; камера с RTSP-адресом подключается в `data/cameras.json`, приём и анализ те же. Трансляция включается кнопкой, анализируется после видео из API и выключается сама через 2 минуты без зрителей. Подробности: `docs/cameras.md`.

### API

Загрузка видео:

```bash
curl -X POST http://79.116.80.166:10171/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
```

Ответ: `{"job_id": "...", "status": "processing"}`.

Получение результата:

```bash
curl http://79.116.80.166:10171/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```

`status` принимает значения `processing` и `done`. Статус `failed` наружу не отдаётся: если анализ не успел или упал, задание всё равно получает `done`, вердикт `violation` и одно нарушение типа «Требуется ручная проверка». Код причины сохраняется в полях `error` и `message`. Так сервис никогда не говорит «нарушений нет», если видео на самом деле не проверено. Формат результата совпадает с разделом 10 ТЗ. Сверх схемы в каждом нарушении есть поля `type_id`, `confidence`, `t_start_sec`, `t_end_sec`, `rule` (`document`, `clause`, `url`) и `boxes` (области на кадрах). Ссылка на правило также продублирована в конце `description`. Запрос без верного ключа получает 401.

Ограничения API: только `.mov` и `.mp4` с видеодорожкой, размер до 2048 МБ. Каждое задание получает финальный статус не позже 285 секунд после загрузки. Страница `/docs` (Swagger) отключена: ей нужны скрипты из интернета.

### Запуск

Сервис целиком работает на одном сервере с GPU (RTX 5090, 32 ГБ) и после загрузки весов не обращается в интернет. Запускаются два процесса.

1. VLM-сервер vLLM с моделью Qwen3-VL-32B-Instruct-AWQ. Слушает только `127.0.0.1:10301`, наружу не открыт:

```bash
HF_HOME=/workspace/.hf_home HF_HUB_OFFLINE=1 vllm serve QuantTrio/Qwen3-VL-32B-Instruct-AWQ \
  --served-model-name vlm --host 127.0.0.1 --port 10301 \
  --max-model-len 26000 --gpu-memory-utilization 0.92 \
  --limit-mm-per-prompt '{"image":16,"video":1}' \
  --media-io-kwargs '{"video":{"num_frames":-1}}' \
  --mm-processor-cache-gb 0 --max-num-seqs 32 --enable-prefix-caching
```

То же самое делает скрипт `app/detector_vlm/deploy/vlm.sh`.

2. Backend:

```bash
git clone https://github.com/ab-dauletkhan/fortethon.git && cd fortethon
uv sync --no-dev
API_KEY=<ключ> DETECTOR=app.detector_vlm VLM_ACTIONS=1 \
  uv run uvicorn app.main:create_app --factory --host 0.0.0.0 --port 10100 --workers 1
```

Backend ждёт готовности VLM-сервера до 15 минут. Пока модель не загружена, `/healthz` отвечает 503. Адрес VLM-сервера задаёт `VLM_URL` (по умолчанию `http://127.0.0.1:10301/v1/chat/completions`). Остальные переменные описаны в `README.md`.

На сервере оба процесса работают под supervisor и перезапускаются при падении. Порядок восстановления сервера с нуля описан в `docs/runbook.md`. Для контейнерного развёртывания backend есть `Dockerfile` и `compose.yaml` с резервированием GPU.

## 3. Архитектура и подход

```
браузер / жюри
   │  HTTP, X-API-Key
   ▼
FastAPI ── SQLite (задания) ── диск (видео, результаты, 24 ч)
   │
   ▼
воркер ── процесс детектора (отдельная группа процессов, убивается по таймауту, получает budget_sec)
   │            │  кадры PyAV по pts, вопросы да/нет
   │            ▼
   │        vLLM: Qwen3-VL-32B-AWQ на GPU (127.0.0.1)
   │            │  P(да) из logprobs
   │            ▼
   │        правила протокола: факты → события
   ▼
сборка результата: вердикт по порогу → тип и правило из каталога → кадры по pts → JSON
```

| компонент | решение |
|---|---|
| API и очередь | FastAPI, одно задание на GPU за раз. Видео жюри идут вне очереди веб-интерфейса |
| надёжность | у каждого задания дедлайн 285 с от загрузки. зависший детектор убивается вместе со всеми дочерними процессами, после рестарта незавершённое задание повторяется один раз. незавершённый анализ даёт «Требуется ручная проверка», а не пустой результат |
| детектор | модель не пишет свободный текст о нарушениях. ей задаются закрытые вопросы да/нет о видимых фактах, ответ читается как вероятность P(да) из logprobs. два прохода идут параллельно, см. ниже |
| правила | факты превращаются в события детерминированными правилами протокола обслуживания: сессия клиента, приём денег, пересчёт, уход кассира. при нескольких событиях одного типа остаётся самое уверенное. нарушения идут в порядке важности: первым стоит основное нарушение видео |
| бюджет времени | детектор получает оставшееся время `budget_sec`. если его мало, он реже берёт кадры и пропускает увеличенные фрагменты и уточняющие окна, но успевает вернуть результат |
| вердикт | «нарушение», если хотя бы одно событие имеет уверенность 0,5 и выше |
| описание и правило | модель описывает только то, что видно. название типа, текст правила, документ и пункт подставляются из каталога `data/rules.json`. **модель не пишет ссылки на нормативы, поэтому выдуманных ссылок быть не может** |
| кадры-доказательства | извлекаются по времени pts, а не по номеру кадра: видео снято с переменной частотой кадров. кадры отдаются без разметки. области передаются отдельным полем `boxes`. они есть у типов про предметы: сейф, ноутбук, деньги, штампы, сумка, напиток, личные вещи, дверь. у типов про людей областей нет намеренно: рамка вокруг человека ничего не доказывает |
| незнакомые нарушения | детектор задаёт закрытые вопросы, поэтому нарушение вне каталога он не опишет. есть два канала без обучающих примеров: «Обзор камеры закрыт» (правило по пикселям: не меньше 45% кадра без текстуры в течение 3 с и дольше) и «Инкассация на виду у посторонних». backend также принимает тип `other` с порогом 0,7, детектор его сейчас не выдаёт |

### Детектор

**Проход STATE (состояние кадра).** Кадр раз в секунду, до 100 кадров на видео. По каждому кадру модель отвечает на 10 вопросов: есть ли кассир, клиент, второй человек на стороне кассира, открыт ли сейф, лежат ли на столе деньги, сумка, напиток, личные вещи. Ответы сглаживаются по соседним кадрам. На первом кадре модель находит стол, ноутбук, сейф и дверь. Когда кассир отсутствует, вопросы задаются по увеличенным фрагментам этих объектов: деньги на столе, ключ в замке, открытый экран, штампы, открытый сейф. Напиток и личные вещи перепроверяются отдельным вопросом по увеличенному кадру.

**Проход ACTIONS (действия).** Видео режется на клипы по 3 секунды (2 кадра в секунду) с шагом 3 секунды. Рядом с передачами предметов добавляются промежуточные клипы. По каждому клипу модель отвечает на 10 вопросов о действиях: клиент отдаёт предмет, работает счётная машинка, кассир передаёт купюры в руки, открывает сейф, принимает или вскрывает сумку, убирает деньги в карман. Отдельный вопрос по неподвижному кадру проверяет, видна ли карточка удостоверения после приёма денег. Её сравнивают с началом сессии, чтобы пачку купюр не приняли за карточку. После входа кассира в кассу клипы проверяют, закрыл ли он за собой дверь.

**Правила.** Пример: «клиент отдал деньги → машинка пересчитала → удостоверение не появилось» даёт `no_id_check`. «Кассира нет больше 2 секунд, клиент у стола» даёт `left_during_service`. Для `no_id_check` таймкод ставится на конец первой передачи денег клиентом, для ухода кассира на момент ухода.

**Бюджет и рамки.** Последними ищутся рамки объектов на кадрах-доказательствах. Если времени осталось мало, рамки пропускаются, а вердикт и таймкоды остаются.

### Модели

| модель | роль | лицензия | размер | где выполняется |
|---|---|---|---|---|
| Qwen3-VL-32B-Instruct, квантизация AWQ 4 бит (`QuantTrio/Qwen3-VL-32B-Instruct-AWQ`, ревизия `c2d44b1`) | ответы да/нет по кадрам и клипам, поиск стола, сейфа, двери и рамок объектов на кадре | Apache-2.0 | 20 ГБ весов | vLLM 0.31.0 на RTX 5090 32 ГБ |

Других нейросетей нет. Правило «Обзор камеры закрыт» считается по пикселям без модели. Обучение и дообучение не проводились. Вопросы и правила подобраны на обучающих видео.

Все модели открытые, с лицензией, разрешающей коммерческое использование, и выполняются на сервере команды. Облачные AI-сервисы не используются ни при обработке, ни при хранении видео. Распознавание лиц не выполняется, звук не анализируется.

4. В результате связь «источник → нарушение → фрагмент видео» выглядит так: пункт акта из каталога, описание видимого действия от модели, таймкод и кадры из видео.

## 5. Распознаваемые типы нарушений

**Уровень a**: прямая норма, нарушение однозначно видно на видео.
**Уровень b**: норма применяется по аналогии или нарушение требует явной картины, поэтому формулировка осторожнее.

**Детектор**: «да» означает, что текущий детектор выдаёт этот тип. «слабо» означает, что правило есть, но на обучающих видео оно срабатывает ненадёжно. Типы с «нет» есть в каталоге и в API, но детектор их не выдаёт: для них не нашлось вопроса, который надёжно отделяет нарушение от нормы (см. раздел 6).

| Деньги предыдущего клиента на столе | a | да | деньги прошлого клиента лежат открыто на столе, пока обслуживается следующий | S1 п. 20 ч. 2 |

| Возможное нарушение кассовой дисциплины | b | нет | действие вне каталога. сервис описывает, что видно, и ссылается на S1 без пункта | S1 |

## 6. Ограничения и известные ошибки

| ограничение | следствие |
|---|---|
| анализ только видимого | сервис не проверяет суммы, подлинность купюр, содержание документов, проводки и сверки. такие нарушения он не заявляет |
| маленький набор | всего 42 видео. вопросы, правила и пороги подбирались на них же, с проверкой на отложенных частях набора. на новых видео точность, скорее всего, ниже, чем в разделе 7 |
| новый ракурс | обучающие видео сняты примерно четырьмя камерами сверху. на реальном видео с другого угла сервис не проверялся. есть только косвенные проверки (раздел 7): вердикты меняются от ракурса, но качество не падает до случайного. фиксированных зон кадра нет: стол, сейф и дверь ищутся на каждом видео заново |
| передача из рук в руки | модель не отличает передачу денег клиенту в руки от передачи через стол. ни один вопрос по клипу, кадру или фрагменту не разделил эти случаи. «Деньги переданы из рук в руки» почти не срабатывает, «Часть купюр возвращена клиенту без оформления» не выдаётся. поэтому пропущено видео X-1 |
| отбракованные купюры | модель путает маленький детектор купюр со счётной машинкой. проверенные и непроверенные отбракованные купюры выглядят одинаково, тип отключён. поэтому пропущено видео Х-44 |
| сейф | правило открытого сейфа настроено по одному положительному примеру (Х-20, уверенность 0,56). сейф должен оставаться открытым до конца записи. другие картины открытого сейфа могут быть пропущены |
| ключ в замке | ключ занимает несколько пикселей. «Ключ оставлен в замке сейфа» ненадёжен даже на увеличенном фрагменте |
| запас уверенности | часть верных ответов близка к порогу 0,5. например, «Деньги приняты без проверки документа» в X-2 имеет уверенность 0,63 |
| документ на телефоне | цифровой документ на экране телефона сверху может быть не виден. тогда возможен ложный «Деньги приняты без проверки документа». белая пачка купюр в руке похожа на карточку, тогда возможен пропуск |
| смартфон | в разметке нет примеров, модель путает телефон с другими предметами. тип отключён |
| роли людей | контролирующего работника, заведующего кассой и постороннего по видео не различить. поэтому тип называется «Второе лицо в кассе», а решение остаётся за проверяющим |
| одно событие на тип | если один тип нарушения случился в видео дважды, сервис покажет только самый уверенный случай |
| нарушения по бездействию | таймкод ставится на момент, когда обязательное действие должно было произойти |
| нагрузка | один GPU обрабатывает одно видео за раз. при одновременной загрузке многих видео последние в очереди получают меньше времени: детектор реже берёт кадры, а если времени не хватило, отдаёт «Требуется ручная проверка» |
| незнакомые нарушения | нарушение, для которого нет вопроса, будет пропущено |

## 7. Качество

Оценка на 42 размеченных видео обучающего набора (40 уникальных, X-47 и X-48 повторяют X-4 и X-5). Прогон через работающий сервис, версия детектора `5ab6ca0` (`app/detector_vlm`). Порог уверенности 0,5.

Разметка расходится с разметкой организаторов в трёх видео. Организаторы отметили Х-35, Х-37 и Х-39 как видео без нарушений. В них клиент сдаёт деньги, а удостоверение в кадре не появляется. Команда решила считать это нарушением «Деньги приняты без проверки документа» (S1 п. 19 пп. 1). Поэтому в нашей разметке нарушения есть в 25 из 42 видео. Если жюри считает эти видео чистыми, сервис на них даст ложное «нарушение».

| версия | точность вердикта | ложные «нарушение» | пропуски | верный тип | медианная ошибка таймкода |
|---|---|---|---|---|---|
| всегда «нарушение» (базовая линия) | 0,595 | 17 | 0 | | |
| v9 (промежуточная) | 0,810 | 3 | 5 | 15 из 25 | 3,0 с |
| **в сервисе (`5ab6ca0`)** | **0,952** | **0** | **2** | **23 из 25** | **1,3 с** |

- точность вердикта: доля видео, где вердикт совпал с разметкой;
- верный тип: в скольких нарушениях из 25 сервис назвал правильный тип;
- ошибка таймкода: разница между таймкодом сервиса и разметкой для верно найденных нарушений.

Пропуски: X-1 (деньги из рук в руки и возврат части купюр) и Х-44 (отбракованные купюры не проверены). Причины в разделе 6.

Отдельной нетронутой выборки нет. Подбор отдельного порога для каждого типа давал 0,833 на всех видео, но 0,43-0,67 при проверке на половинах набора. Поэтому такие пороги не используются, у всех типов один порог 0,5.

### Время обработки

| условия | время на видео |
|---|---|
| одно видео, GPU свободен, все 42 видео | медиана 21 с, максимум 67 с |
| 5 самых длинных видео загружены одновременно | 33, 76, 120, 168 и 209 с от загрузки, все меньше 270 с |

Видео обрабатываются по очереди, поэтому пятое ждёт четыре предыдущих. Ему осталось меньше времени, детектор взял кадры реже, а вердикт остался верным.

Видео с другого угла у команды нет. Есть только косвенные проверки.
